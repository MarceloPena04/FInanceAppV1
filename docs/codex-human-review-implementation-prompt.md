## Implement now

Exact replay after refresh must not duplicate an event or undo a user choice. Choose the smallest local/test mechanism that satisfies this; state its limits.
2. Connect fictional fixture processing to a visibly functional review path. A compact candidate card shows amount, currency and its source/user-rule basis, merchant or source description, date and its basis, event type, current detected impact, confirmation state, and a clear reason for attention. The person can inspect the relevant source excerpt and later source changes without reconstructing the transaction manually.
3. Implement `Confirm`, `Save and confirm`, correction of amount/currency/date/event type/display label, optional comment/category, reversible exclusion, field-level correction undo, and permanent event deletion. Deletion removes event content and history from visible/persisted records but retains only a disclosed minimal replay-suppression marker. Reprocessing the deleted fictional source event must not resurrect it. Never claim that every trace was erased while a marker remains.
4. Implement two bulk actions. The prominent one confirms routine eligible candidates after previewing count and money impact. The secondary one confirms all eligible candidates only after showing flagged items, material changes, possible duplicate double counting, and expected impact. Neither action classifies an unknown event, invents currency, or resolves a duplicate. Candidates with unknown type or no usable currency are ineligible for confirmation until resolved. A possible duplicate may remain counted twice and may be confirmed as two separate displayed records without automatically settling the duplicate relationship.
5. Preserve the existing strict exact duplicate rule. For possible duplicates, provide `Same event`, `Separate events`, and `Decide later`, with reversible decisions and clear metric effects. A referenced finalized observation replaces the system's previous source reading whether higher or lower; a material change returns the event to pending review, displays old/new evidence, and preserves any user override.
6. For detected events with amount and currency but unknown event type, count a separately labelled **provisional outflow** before confirmation. Keep event type unknown; do not turn the assumption into a source fact. Such an event remains ineligible for confirmation until the person classifies it. Missing-currency candidates remain visible and separate from currency totals. Allow a user to opt into a fictional source-profile currency fallback; show the applied currency as coming from that rule, and always prefer an explicit source currency.
7. Compute a calendar-week detected summary by currency with inflow, outflow, net flow, pending contribution, provisional assumed-outflow contribution, period, source coverage, and counts that could not be aggregated. Use and label UTC only as the fictional demo's timestamp-grouping convention; do not treat it as a future user-timezone policy. Confirmation must not change impact twice. Exclusion, corrections, duplicate resolution, finalized updates, and deletion must update the summary once.
